The Heuristic Agent

A probabilistic policy over every decision in the game — fast enough for a 100-seed matrix run and good enough to score touchdowns. A standalone policy, not a search: no tree, prior, value head or playout is in scope. Implemented and measured — §16 has the 100-game A/B against uniform sampling over an identical action space.

    Why a third agent

    The two existing agents are both structurally incapable of playing Blood Bowl. That is by design for one of them — and an accident of inheritance for the other.

    The consequence, measured: across 57,258 activations in 200 parity games, no activation ever moved more than one square and no game ever scored a touchdown. That blocks GFI, scoring, and the whole Punt family — 33 of 200 steps are never dispatched.

    Random play never scores, so every step downstream of a touchdown is unreachable and the reds we do find cluster in the first 20% of a drive. The numbers are in §0.5 →

    Three requirements, in priority order

    1. Probabilistic — every legal option gets non-zero probability. No option is pruned to zero, coverage lives in the tail, and a policy that can only ever produce its favourite move stops being a sampler.
    2. Fast — O(board) per decision, no game-tree search, no cloning of Game. Budget: < 100 ms of agent time per game (§9).
    3. Good — the mode of the distribution should be a move a competent coach would make. Good play is what reaches the endzone, and reaching the endzone is what unlocks the dead steps.

    /// One legal option with its heuristic desirability.
pub struct Weighted {
    pub action: Action,
    /// SIGNED desirability, roughly [-1, 1] — §5.3 subtracts an expected turnover
    /// cost, so a genuinely bad option scores below zero. Softmax is
    /// shift-invariant, so negatives are fine. A logit input, never a probability.
    pub weight: f32,
    /// A `&'static str` cannot carry the numbers §6's rules produce, and §9 forbids
    /// `String` in the hot path — so rule and number are stored separately.
    pub why: Rule,
    pub why_value: f32,
}

/// What `score` fills in. A struct rather than a bare Vec so a capped candidate set
/// is never mistaken for a genuinely small one — and so the buffer can be reused.
pub struct Scored {
    pub options: Vec<Weighted>,
    pub truncated: bool,
}

/// The scoring half — pure, deterministic, no RNG. Writes into a caller-owned
/// buffer: a Move prompt has ~200 options, so returning a fresh Vec would
/// allocate on every single move.
pub trait Policy {
    fn score(&self, gs: &GameState, out: &mut Scored);
}

    Rule is a #[repr(u8)] enum with one variant per §6 clause; the pair (why, why_value) reconstructs every explanation in this document, formatted only under #[cfg(feature = "agent-trace")]. truncated is set wherever an option set is capped — §6.5's activation candidates, §6.30's inducement subsets, §6.39's multi-block pairs — and paired with a log() line naming what was dropped.

    

        
    Softmax, and why temperature is the real knob
    
        
    The weights in the brief (0.9 / 0.8 / 0.05 …) live in [0, 1]. A plain softmax at T = 1
        over that range is almost uniform — exp(0.9)/exp(0.05) = 2.3, so "Attacker Down" would be
        picked 20% of the time against "Defender Down". That is not what the numbers mean. They read as
        strong preferences, so temperature is what turns the stated weights into the intended
        behaviour — and it is per prompt class, not global.

    Two floors are non-negotiable.
    
          
    T > 0 always — never argmax; coverage dies without the tail.
          ε-floor — after softmax, mix with uniform: p ← (1−ε)·p + ε/n at ε = 0.02.
          That makes "consider ALL actions" literal even when the weight spread is extreme, and guarantees a
          long coverage run eventually reaches every branch.
    
        
    

        
    Why score and sample are separate
    
        
    Policy::score is pure and RNG-free; HeuristicAgent::act is the only thing
        that touches the RNG. That split costs nothing and buys three concrete things:
    
        
      
          
    • Testability — every §6 heuristic can be asserted on directly, with no RNG to stub. §10.1's
            ordering tests all call score.
      • 
          
    • Traceability — dumping the scored option set with its why strings explains
            any decision the agent made, which is how a bad weight gets found.
      • 
          
    • Benchmarking — §9's budget is measured on score, the part that actually
            costs anything.
      • 
        
    
        
    HeuristicAgent must be deterministic given (state, rng state). No HashMap
        iteration order in any scoring path — enumerate from sorted vectors only. Same discipline the parity
        agents already follow.
    
        
    
          
    Motivation, not scope. This is also the interface a Monte-Carlo tree search would want if
          one is ever built — scores as a prior, near-zero temperature for playouts. That is a reason the
          split is worth keeping, not a thing to build here. Nothing in this document specifies a
          search, and no engine change is to be made on its behalf.
    
        
    
      
    

      
      
    
        
    §2
    Numeric primitives
    
        
    Inline, allocation-free, shared by every heuristic. All of them delegate target
        numbers to the mechanics crate rather than re-deriving them.
    

        
    /// P(d6 >= target), with the natural-1-fails / natural-6-succeeds rule the engine
/// already applies in DiceInterpreter::is_skill_roll_successful.
pub fn p_roll(target: i32) -> f32 {
    ((7 - target) as f32 / 6.0).clamp(1.0 / 6.0, 5.0 / 6.0)
}

/// A roll that may be re-rolled once. `p_rr` is 1.0 for a skill re-roll (Dodge, Catch,
/// Sure Feet, Sure Hands, Pro); for a team re-roll under Loner(n) it is p_roll(n).
pub fn p_with_reroll(p: f32, p_rr: f32) -> f32 { p + (1.0 - p) * p_rr * p }

/// A move path is a chain of independent rolls — dodges, GFIs, a terminal pickup.
pub fn p_chain(steps: &[f32]) -> f32 { steps.iter().product() }
    
          
    2+ = .833 · 3+ = .667 · 4+ = .500 · 5+ = .333 · 6+ = .167. A 4+ with a free skill re-roll is .75; with a Loner(4) team re-roll, .625.
    
        
    

        
    Block-dice equity
    
        
    The declaration heuristics (§6.5) score a block before the dice are rolled. An earlier
        draft carried six hand-set constants and bolted skills on afterwards as multipliers — which can never
        cover the combinations, since Block, Wrestle, Dodge, Tackle and Fend interact and a 1-die block with
        Block is a completely different proposition from the bare 1D the constant describes.
    
        
    The quantity is a closed form: over |n| dice there are only
        6^|n| equally likely outcomes. Compute the whole table once at startup —
        block_equity(n, BlockSkills) — and read it with two array indices forever after. The same
        function supplies §6.4's E[best], so the re-roll decision and the declaration decision can
        never disagree. Context that is not a skill (out-of-bounds pushes, ball possession, tempo)
        stays a multiplier on top, in §6.2.
    
        
    The skill-less row reproduces the brief's calibration closely enough to keep it as the pinned sanity
        check:

    §4
    The move engine
    
        
    The most valuable component, the one that unblocks the dead-step frontier, and the
        only place the design deliberately breaks with the existing agents' behaviour.
    

        
    
          
    The shape of the problem. AgentPrompt::Move offers only the eight adjacent
          squares, so a "movement decision" looks like a sequence of up to MA + 2 single-square
          decisions — and the existing agents end the activation after the first one.
    
        
    

        
    The engine already walks a whole path
    
        
    Verified in the code, not assumed. Action::Move { path } is handled by each
        edition's StepInitMoving::handle_command, which stores the entire path in
        self.move_stack (step/bb2025/move_/step_init_moving.rs:70).
        execute_step pops one square per pass (:245), republishing the
        remainder as StepParameter::MoveStack, and AgentPrompt::Move is emitted
        only when the stack is empty (:376). It is a faithful port of Java's
        fMoveStack.
    
        
    
          
    Submitting Action::Move { path: [a, b, c, d, e, f] } walks all six squares — dodges,
          GFIs and all — with zero further Move prompts.
    
          
    Both current agents send vec![single_square]. The step-by-step protocol is an
          agent convention, not an engine constraint — and it is the whole reason the measured maximum
          in §0.5.1 is exactly 1.
    
        
    

        
    So: submit the whole path
    
        
    Given the above, a plan-and-walk cache solves a problem that does not exist. Answer the first
        Move prompt with the complete path and let the engine walk it.
    
        
    let reach = reachable(&gs.game, &features, player_id);      // one Dijkstra, ~20 µs
let dest  = sample_softmax(&mut self.rng, &score_all(&reach), T_MOVE);
Action::Move { path: reach[dest].path.clone() }             // the whole thing, in order
    
        
    That removes the MovePlan cache, the stamp-lineage bookkeeping, the "is the next
        planned square still offered" check, and N−1 agent re-entries per activation.
    
        
    Be honest about the size of the win. The prompt loop is in-process function calls, not IPC,
        so the round-trips were never expensive — a 6-square move costs 20 µs + 6 × 1 µs either way. The real
        saving is one Dijkstra instead of a cache-validity decision per square, and far less agent state. Take
        it for the simplicity, not the microseconds.
    
        
    What still interrupts. The engine will still prompt mid-path for dodge re-roll offers, skill
        uses, Diving Tackle, Shadowing and Fend — different prompt variants, answered by §6.14 and §6.16. Only
        the movement decision is pre-committed.
    

        
    The blocker: is_valid_move is ported but never called
    
        
    
          
    UtilServerPlayerMove::is_valid_move exists and is correct
          (util/util_server_player_move.rs:61) — it checks the acting player is actually at
          coordinateFrom and drops the command if not. No edition's
          StepInitMoving calls it. All three carry the explicit comment
          "no-op: UtilServerPlayerMove.isValidMove path validation not ported; agent-submitted paths are
          trusted."
    
          
    Java calls it in handleCommand. Today the gap is invisible because both agents
          submit one square at a time and it is always valid. Submit a six-square path, let a Diving Tackle
          relocate the player at square three, and the engine keeps popping the original coordinates —
          the player teleports, where Java would have dropped the command as out-of-sync.
    
          
    Turning multi-square movement on is exactly what surfaces this latent divergence. Wire it
          in first — a call to an already-ported function plus a re-prompt on failure — as a prerequisite of
          phase 4, not a follow-up.
    
        
    
        
    The re-prompt on failure also hands the agent its re-planning trigger back, for free and in the
        right place: the engine says "your path is stale", the agent re-runs reachable from where
        the player actually is.
    

        
    Free input the engine already computes
    
        
    UtilServerPlayerMove::update_move_squares is fully ported and writes
        field_model.move_squares, where every MoveSquare carries
        minimum_roll_dodge and minimum_roll_gfi
        (types/move_square.rs:14) — the engine's own target numbers for each square adjacent to
        the acting player. Use them for step 1 of any path and keep the computation below for steps 2..n,
        since the set only refreshes as the player actually moves.
    

        
    Probability-weighted reachability
    
        
    The existing PathFinderWithPassBlockSupport is a distance A*: it blocks tackle
        zones outright rather than costing them. That is the wrong objective. The agent needs "cheapest
        in expectation", where a dodge is a probabilistic cost, not a wall. New module,
        agent/reach.rs, leaving the existing pathfinder untouched.

    §5
    The value model
    
        
    reachable says can I get there and how likely. The value model
        says do I want to be there.
    

        
    V(sq, p) = base_intent(sq, p) · sideline(sq, p) · exposure(sq, p) · lane(sq, p)

weight(sq) = p_arrive(sq) · V(sq, p)  −  (1 − p_arrive(sq)) · c_turnover(sq, p)
    
        
    
          
    This is an expectation, not a discount. An earlier draft used
          p_arrive · V · gfi_penalty, which prices a failed dodge as "you gain nothing".
          In Blood Bowl a failed dodge, a failed rush or a fumbled pass ends the team turn: every player
          who has not yet acted is forfeited, and possession usually goes with it. Multiplying by
          p_arrive has no term for what is lost.
    
        
    
        
    let unactivated = f.tempo.eligible_remaining as f32 / 11.0;
let c_turnover  = (0.20 + 0.55 * unactivated)      // early in the turn it costs far more
                * if carries_ball { 1.4 } else { 1.0 }
                * (1.0 + 0.15 * gfi as f32);       // a failed rush also drops the player
    
        
    Three correct behaviours fall out of this and are written nowhere else: risk migrates to the end
        of the turn (with ten players still to act c_turnover ≈ 0.70; with one, ≈ 0.25), a
        6+ dodge becomes negative rather than merely small — at p = 0.167 a square would have to be worth
        more than 3.5 to break even, and nothing is — and the carrier stops running through three tackle
        zones on turn 1, with no special case for it. The gfi term replaces the old
        gfi_penalty table for a stated reason: a failed rush is a turnover plus an armour
        roll on the player who fell.
    
        
    
          
    Recalibrate §8 after this lands. Weights are now signed and their spread is wider, which
          makes any fixed temperature effectively sharper. §8's values were measured on the multiplicative
          form (§7.7a) — re-run that sweep and judge by top-20 mass. §10.4 is the mechanism.

    Urgency — the clock
    
        
    A drive is a multi-turn plan, and whether it can still finish changes every weight on the board.
        Nothing in an earlier draft of the value model knew what turn it was.
    
        
    let turns_left     = (TURNS_PER_HALF - turn_nr).max(0);          // 8 per half
let turns_to_score = ((d_sq as f32) / (ma as f32)).ceil() as i32;
let slack          = turns_left - turns_to_score;
let urgency        = (1.0 - slack as f32 / 3.0).clamp(0.0, 1.0);
    
        
    urgency multiplies the carrier's base_intent by
        0.75 + 0.5 · urgency — a patient turn 1 is 0.75, a turn-7 sprint is 1.25 — and scales
        w(EndTurn) by 1 − 0.4 · urgency. With the half running out, stopping early
        gets less attractive at exactly the rate scoring gets more so.
    
        
    And advance is measured against what the activation could achieve, not against
        the distance remaining: advance = (d_now − d_sq) / min(d_now, MA + 2). The earlier form
        divided by d_now, making the same six squares worth 0.50 from d = 12 and 0.25 from
        d = 24 — it quietly told a deep carrier that running was only half as useful.
    

        
    Sideline, exposure and lane
    
        
    Sideline squares invite a push-out crowd-surf — for a carrier, a turnover and an injury
        roll. The pitch is x ∈ 0..=25, y ∈ 0..=14, sidelines at y == 0

        y == 1 / y == 13 for a carrier, because one push from there reaches the crowd.

    lane — is anything actually in the way?
    
        
    base_intent is a pure function of |x − endzone|, so without a lateral
        term every square in a column scores identically: §7.2 ties five squares at the best weight and §7.3
        ties ten, visible as bands in the heatmaps. lane is that missing signal, and it is a real
        one rather than a tie-breaker — running into an empty corridor is worth more than running into the
        pack.
    
        
    // opponents within ±2 rows of sq.y, between sq.x and the endzone —
// two prefix reads per row, using BoardFeatures::row_prefix (§3)

    .filter(|y| (0..=14).contains(y))

    Three spec bugs this exercise exposed
    
        
    Running the numbers on real boards found problems that reading the spec did not — and two more
        (D11, D12) turned up when the examples were recomputed after the §14 pass.
    

        
    
          
    (a) The temperature table was calibrated for small option sets. §8's temperatures were
          chosen against a 2–5 option decision like block dice. A Move prompt has ~200 options,
          and softmax spreads mass over all of them. Measured below as the mass held by the twenty best
          destinations — not the top five, which is unusable here: §7.3's board ties ten squares at the
          best weight, so a top-5 metric reports a failure that is really a tie.

    Probability mass held by the twenty best destinations, as temperature falls. At the specified T = 0.20 the top twenty out of ~200 hold barely a fifth of the mass — a slightly-biased random walk, which is the exact failure the agent exists to replace.
    
        
    
        
    §8's Move temperature is corrected to 0.06, and so are the three other
        prompts that had inherited a small-set value — KickBall, PuntTarget and
        ThrowTeamMateTarget. The table now carries the rule that made the error possible:
        a temperature is only meaningful against an option count, so it lists the count alongside every
        row and the lookup takes both. Judge by top-20 mass or the tied-best tier, never top-1 and
        never top-5.
    

        
    
          
    (b) The value function had no lateral preference. In §7.2 the five best destinations are
          (9,8) … (9,12) — an entire column, at identical weight; §7.3 ties ten. At the time this was written,
          base_intent for a carrier was a pure function of endzone_distance =
          |x − ez|, so every square in a column scored the same and only sideline
          and exposure broke the tie.
    
          
    §5.1 now carries a lane term for exactly this — opponents in a five-row
          corridor between the square and the endzone, read in O(1) off §3's row_prefix. Running
          into an empty corridor is worth more than running into a three-man screen, which no other term
          expressed. Ties will not vanish, and should not: two genuinely equivalent squares ought to tie. They
          stop being the default outcome of a column.

    §11
    Parity implications
    
        
    The constraint that most easily gets violated. Read before touching anything shared.
    
        
    
          
    RandomAgent must not change. Its decision/action RNG consumption order is
          byte-matched against ParityRunner.java. HeuristicAgent is a new type; it
          shares helpers only through pure, RNG-free functions.
    
        
    
        
      
          
    • The parity matrix keeps running on RandomAgent. Improving coverage does not
            make the heuristic agent a parity driver — a parity run compares Rust against Java, and Java's
            ParityRunner makes the other half of every decision.
      • 
          
    • To use it for parity, every heuristic in §6 must be ported to
            ffb-ai/ParityRunner.java and produce identical picks from identical draws. Then:
            scoring must be integer milli-weights (0.90 → 900), not f32 —
            cross-language float ordering is not guaranteed identical and a tie broken differently is a desync;
            softmax runs over a shared integer exp lookup table; and the RNG draw count per prompt
            class must be fixed and documented as AGENT_CONTRACT.md does today (one draw per
            sample, always, even when n == 1).
      • 
          
    • Recommended path is staged — land the agent for coverage sweeps first (no parity risk
            at all), measure the coverage delta, then decide whether the Java port earns its cost.

    The agent is implemented —
        crates/ffb-engine/src/agent/heuristic_agent.rs, driven by
        ffb-parity --heuristic <temp_scale>. The control arm is the same agent with
        temp_scale = 1e6, which flattens every softmax so it samples uniformly over exactly the

          was an artifact, and the reader who distrusted it was right. Four defects, found by measuring
          rather than reading:

    The bug that mattered: the agent had never valued the ball
    
        
    
          
    Board::ball_live was ball_in_play && !ball_moving, and the
          Pickup intent was gated on ball_live && carrier.is_none().
    
          
    In this engine ball_moving == true means the ball is LOOSE on the ground, not
          in flight — the legal_actions tests say so directly. So ball_live meant
          carried, and the gate read "the ball is carried AND nobody is carrying it" — a
          condition that can never hold.
    
        
    
        
    In a trace of 754 movement decisions: Pickup fired zero times;
        Cage and Screen were gated on a carrier that was None 82% of
        the time; Retreat — the flat 0.10 floor — won 642 of 746 non-carrier decisions;
        and the carrier moved 8 times in 754. The agent had no ball-oriented behaviour at all.

        hiding.

            sharp arms cover 36 event types where the sampled arm covers 37.
      • 
          
    • Agent time is 11.5× the budget — §18, entirely the missing caching layer
            (P5–P7).
      • 
          
    • Dead-step coverage is unmeasured. The 167/200 figure predates all of this. It should move
            — scoring alone unlocks five category-C steps — but that is a prediction, not a
            measurement.

      20.1
      Move → Move never makes sense — end the activation eagerly
      high value−10%
    
    
    Measured: 35.7% of all Move prompts are a consecutive Move-then-Move with nothing in
  between — 2049 of 5746 over ten games. Mean 2.07 move answers per moving activation, with
  a tail out to seven. Every one is a full ~200-option re-plan reaching the same place a single longer path
  would have reached.
    
  
    SequenceNew options?
    
  
    Move → MoveNo. Same options, worse path. Never correct
    
  
    Move → Pass / Hand-offYes — a throw is not a move
    
  
    Move onto the ball → MoveYes — it is a carrier now; the value model changed
    
  
    Blitz: Move → Block → MoveYes — the board changed underneath it
    
  
    Stand up → MoveYes — it could not move before
    
  
    
  
    Fix: a small state machine on the activation, not a scoring decision. After a plain
  move with no acquisition and no block, the next Move prompt is answered
  EndPlayerAction for free. Removes ~2050 re-plans and makes the ~1780 end-of-activation answers
  free too — about two thirds of all Move cost.
    
  
    
    
      20.2
      Plan once at declaration; replay it afterwards
      −8%
    
    
    The ActivatePlayer scorer already ran reachable for the player it chose and
  already knows the destination and path. The Move prompt then throws that away and recomputes
  it.
    
  
    Fix: cache the winning (player, action, destination, path) from the
  activation decision and serve the following Move prompt from it. One Dijkstra and one value
  sweep saved per activation, and it composes with 20.1.
    
  
    
    
      20.3
      Two-tier activation scoring — the fix the spec already specifies
      −55% of ActivatePlayer
    
    
    §6.5.1 says: cheap proxy for every eligible player, full search for the top three. The build does
  neither — it runs reachable per player in the Move branch and again in the Blitz
  branch, up to 22 Dijkstras for one prompt.
    
  
    Fix: the proxy needs no search at all — carrier or not, marked or not, prone or
  not, best block dice from where it stands, distance to the ball, and the best of its eight adjacent squares.
  That resolves every rule in §6.5.1 except "free mover".
    
  
    
    
      20.4
      Rasterize the value field once per position change
      −60% of the remainder
    
    
    value_of is called per square, ~200 times per Move prompt and again for
  every activation candidate. But most of V does not depend on who is moving:
  threat, lane, sideline, the cage geometry and the distances to ball
  and carrier are properties of the square. Only advance, urgency and the
  MA cap are mover-specific, and those are closed forms.
    
  
    Fix: precompute two [f32; 26*15] rasters, one per side, whenever
  positions change. Per-square scoring becomes an array read plus three multiplies.
    
  
    
    
      20.5
      Rasterize the threat map specifically
      
    
    
    The worst offender inside 20.4, worth naming separately: threat_on walks all 22 players
  for every square, so scoring a 200-square prompt costs ~4400 player visits — and
  path_share walks them again for the Screen intent. One pass fills the raster;
  every read after is O(1). This is P5 and B6, still unimplemented.
    
  
    
    
      20.6
      Give the Dijkstra real data structures
      3× inside reachable
    
    
    reachable uses a HashMap<FieldCoordinate, …> for the visited set, a
  linear scan over the frontier to find the minimum (O(n²) in ~200 nodes), and clones the whole path
  Vec on every improvement.
    
  
    Fix: a flat […; 390] array indexed y*26+x, a
  BinaryHeap, and back-pointers — reconstructing the path exactly once, for the destination
  actually chosen.
    
  
    
    
      20.7
      Cache and lazily build the board features
      
    
    
    Board::new() rebuilds the tackle-zone map, row prefixes and carrier scan on every
  act() — including the ~60 prompts a game (BlockChoice, FollowUp,
  Pushback, ReRollOffer) that never read any of it. Key it on a positions stamp
  (P5/B3) and build each part on first use. During one team's turn the opponent does not move at all, so most
  of it is invariant for the whole turn.
    
  
    
    
      20.8
      Memoize block_target_weight per (attacker, defender)
      
    
    
    It calls find_block_strength twice, and that function runs a nested player × player
  loop for the Guard-cancel rule — roughly 484 iterations per call. It is invoked from the
  Block branch, the Blitz branch and the BlitzTarget handler, often for
  the same pair several times in one prompt. A small memo table keyed on the pair, cleared with the positions
  stamp.
    
  
    
    
      20.9
      Make the action space whole plans, not fragments
      high valuefixes two bugs too
    
    
    The generalisation of 20.1, and the most valuable item here because it is a correctness fix as
  much as a speed one. Enumerate an activation as (player, plan):
    
  
    Block(victim)                    Foul(victim)
MoveTo(sq)                       MoveTo(sq) + Pass(receiver)
Blitz(victim, via sq)            MoveTo(sq) + HandOff(receiver)
Pickup(ball) + MoveTo(sq)        StandUp + MoveTo(sq)
    
  
    The engine's follow-up prompts are then replayed from the plan instead of re-decided: one scoring
  pass per activation instead of the current 3.4. And it makes two things expressible that currently are
  not:
    
  
      
    
    • move-then-pass, which the fragmented design cannot represent at all — the reason passing
      is dead (§19.3);
      • 
    
    • blitz-to-a-specific-victim, with the movement constrained to squares adjacent to the chosen
      victim — the reason the blitz never blocks (§19.2).
      • 
  
    
  
    Two bugs and a speed-up from one restructuring. This is the item to do first if only one
  gets done.
    
  
    
    
      20.10
      Prune before scoring, and skip the trivial
      
    
    
      
    
    • Admissible bound. With a sharp temperature, any option more than ~10·T below the maximum carries
      under 1e-4 of the probability. Compute an optimistic p_arrive_upper × V_upper per
      destination straight off the raster, fully score only the top K, and put the rest in one sampled tail
      bucket that keeps the ε-floor's guarantee intact.
      • 
    
    • Short-circuit trivia. Return immediately when an option set has one element instead of running
      softmax over it; reuse scratch buffers rather than allocating a HashMap and a path
      Vec per reachable call.

    §20.9 is what fixed the blitz
    
        
    The blitz was declared 7.8 times a game and produced a block zero times (§19.2). Two
        defects: the folded target and the BlitzTarget answer disagreed, and the
        Move handler did not know it was in a blitz. The plan model fixes both at once —
        the victim is chosen once, the path is constrained to a square adjacent to it, and on arrival the
        agent sends the Action::Block that StepInitMoving dispatches as the blitz.
        0.0% → 84.4%, worth 5.6 extra blocks a game that were previously paid for and never
        received.
    

        
    Three bugs measurement caught and reasoning did not
    
        
    
          
    1. The "admissible bound" in §20.10 was admissible, but its ranking was not.
          Sorting destinations by p_arrive and keeping the top 24 keeps every one-square shuffle
          (p = 1.0) and discards the six-square scoring runs (p ≈ 0.3) — exactly the moves that
          score. Touchdowns fell 1.76 → 0.19. After §20.4's rasters the full value
          computation is a handful of multiplies over ~90 squares, so the pruning was buying nothing and
          paying for it in touchdowns. Removed; the code now carries the post-mortem so nobody re-adds it.
    
          
    2. StepInitMoving guards every folded dispatch and falls through when the
          guard fails, re-emitting the same Move prompt. Resending a rejected terminal action
          spun forever. Each is now gated on the engine's own condition and latched so it is attempted at most
          once per activation.
    
          
    3. The all-players-used backstop went missing in the rewrite. An activation that ends
          without moving leaves the engine's eligible list unchanged, so used_this_turn is the
          only thing making progress; without it the driver livelocked.
    
          
    Both hangs presented identically — 200,000 decisions, ActivatePlayer and
          Move alternating — and neither was visible from reading the code.
    
        
    

        
    One item measurement rewrote
    
        
    
          
    §20.7 said "cache the board features". Caching alone made the cheap prompts worse:
          building the rasters for a BlockChoice took it from 11 µs to 86 µs,
          and BlockChoice reads none of them. The fix is the three tiers §20.7 actually
          specified — prompts that read nothing about the board, prompts that read only the cheap core

          its own: BlockChoice 86 → 7.6 µs, Pushback 78 → 5.4,
          FollowUp 80 → 4.6.
